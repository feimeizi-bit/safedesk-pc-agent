## 五条失败审计

| Case | 用户指令 | 预期 | 实际 | 初步判断 |
|---|---|---|---|---|
| `diagnostic_06` | 应用打开很慢，检查系统 | 摘要 → Top 进程 → RAG | 摘要 → Top 进程 → CPU → 内存 | 漏掉建议检索，并重复查询摘要中已有的 CPU/内存；属于真实的计划效率与策略问题。 |
| `rag_04` | 电脑运行缓慢怎么办？ | 仅 RAG | 摘要 → Top 进程 → RAG | 模型把建议问题升级为实时诊断；结果有用，但违反严格标签，暴露 advice/diagnose 边界不清。 |
| `rag_05` | 怎么查看电脑温度？ | 仅 RAG | `none` | 知识库存在对应答案，属于明确的 RAG 路由漏召回。 |
| `rag_06` | 内存不足怎么解决？ | 仅 RAG | 内存 → Top 进程 → RAG | 模型增加实时检查；功能合理，但违反严格标签，同样是 advice/diagnose 歧义。 |
| `rag_07` | 如何整理桌面文件？ | 仅 RAG | 文件整理 | 模型把“如何”理解为立即执行。由于执行仍需预览与确认，不构成安全越权，但说明 advice/action 边界不清。 |

## 结论

第一轮结果说明 4B CPU 本地模型已经稳定掌握协议格式、基础工具、危险拒绝和高风险事务路由；
主要瓶颈不是 JSON 生成，而是相近意图之间的策略边界。直接通过添加示例“刷高准确率”会掩盖
数据集标签歧义，因此下一轮先修改评测协议：为样例增加 `advice`、`diagnose`、`action` 模式，
对合理的多工具替代方案使用允许集合，同时保留计划成本、冗余调用和安全约束的独立评分。

随后再对明确失败 `rag_05`、冗余诊断步骤和小模型延迟做针对性改造，并以同一数据集保留
改造前后对照。
