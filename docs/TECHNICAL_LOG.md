# SafeDesk 长期改造技术日志

这是一份持续追加的工程日志，不是完成后补写的宣传文档。每次重要改造都应记录：
问题、假设、方案、对照实验、结果、失败案例和下一步。未经重新测量，不覆盖历史指标。

## 项目目标

在消费级 CPU、4B 量化本地模型和有限上下文条件下，构建一个安全、可恢复、可审计、
可评测的 Windows Agent Runtime。模型负责语言理解和有限规划；确定性程序负责权限、
执行、验证和恢复。

## 2026-07-22：改造前基线

### 已验证能力

- Qwen3.5-4B-Q4_K_M 通过 llama.cpp 在纯 CPU 环境运行。
- 7 条工具路由样例中，修正终端编码后验证了单工具、双工具、闲聊和危险请求输出。
- 单次路由耗时约 8.55～12.34 秒；此前包含完整 Agent 调用的一次 CPU 查询约 17.74 秒。
- 本地 embedding 缓存可以离线加载。

以上只是可行性样例，不应当作正式准确率。正式指标必须来自固定数据集和批量运行。

### 基线缺陷

1. `open_app` 接受任意字符串并使用 `shell=True`，存在命令注入风险。
2. 文件路径检查使用 `auto_confirm=True`，绕过原本设计的确认流程。
3. Agent 无条件将审计状态写成 `user_confirmed=True`。
4. `none` 被当作未知工具；非法参数会抛出 `TypeError`。
5. 五轮循环实际在第一轮全部返回，不构成真正的观察/恢复循环。
6. FastAPI 异步端点直接执行同步模型推理，阻塞事件循环。
7. 审计数据库固定写入用户主目录，部署环境不可移植。
8. RAG 向量库包含重复、过粗的问答块；查询“批量重命名”曾错误返回“PDF 转 Word”。
9. 缺少 PC Agent 专属测试、README、依赖清单和 Git 忽略规则。

## 2026-07-22：v0.1 安全地基

### 本次实现

- 新增 Pydantic 工具调用协议，禁止额外字段，限制单计划最多五个调用。
- 新增声明式工具注册表和只读/低风险/高风险分级。
- 未知工具、非法 JSON、错误参数均 fail closed，不执行任何操作。
- 高风险计划执行前统一预检，避免先执行部分安全工具后才遇到审批。
- 文件整理增加非修改预览、显式确认和同名冲突拒绝。
- 应用启动改为固定白名单和 `shell=False`。
- 审计数据库支持 `PC_AGENT_AUDIT_DB`，默认写入项目 `.pc_agent` 目录。
- 审计参数改为 JSON，记录真实确认状态。
- FastAPI 使用线程池承载同步推理，并传递真实确认字段。
- Gradio 增加高风险确认复选框，提交后自动复位。
- RAG 从前三条检索结果中解析独立问答并进行问题匹配，避免固定取最后一个答案。
- 新增独立 `tests/`，避免旧学习脚本被 pytest 误当成项目测试。

### 当前明确限制

- 确认仍然是请求级布尔值，未绑定计划哈希，存在确认内容与最终计划不一致的空间。
- 文件操作还没有事务日志和回滚。
- Agent 执行完工具后尚未再次调用模型生成自然语言总结。
- 工具顺序是列表，不支持依赖图和基于 observation 的重新规划。
- RAG 构建流程尚未清理历史重复向量，也没有正式检索评测集。
- 本地模型仍配置 `n_ctx=1024`，不足以承载较长轨迹。

### 验证结果

- `python -m pytest`：10 passed，耗时 1.02 秒。
- 真实 Qwen3.5-4B Runtime 调用“CPU 使用率是多少”：成功选择并执行只读工具，耗时 12.34 秒。
- `PC_AGENT_OFFLINE=1` 下查询“如何批量重命名文件”：返回正确 F2 操作说明和来源，耗时 8.07 秒。
- RAG 加载仍产生 `HuggingFaceEmbeddings` 弃用警告，计划迁移到 `langchain-huggingface`。

验证环境为当前开发 PC 的已有虚拟环境和模型缓存，尚不代表全新环境可复现性。

## 架构决策记录

### ADR-001：不信任模型输出

模型输出只被视为候选计划。工具名、参数、权限和确认状态全部由 Runtime 独立判断。
拒绝依赖 System Prompt 作为唯一安全边界。

### ADR-002：高风险计划先整体预检

如果一个多工具计划包含高风险工具，在确认前不执行任何步骤，避免产生部分副作用。
后续引入事务后再支持分阶段提交。

### ADR-003：第一阶段保留现有目录入口

为降低一周改造风险，暂时保留 `API/main.py`、`frontend/ui.py` 等入口，先建立协议和测试。
稳定后再迁移到 `src/pc_agent/` 包结构。

### ADR-004：单桌面采用拒绝式准入，不建立隐藏队列

控制接口可以并发响应，但模型与有副作用的桌面执行面同一时间只允许一个活动任务。
忙碌时返回 `503 agent_busy`；取消和超时采用协作式语义，工作线程真正退出前不释放
容量。这样可以避免 API 已返回超时、底层原生推理仍运行时错误地启动第二个任务。

## 2026-07-23：v0.2 计划绑定与失败补偿

### 问题

v0.1 使用请求级布尔确认。用户看到预览后需要重新发送原指令，模型可能生成不同计划；
即使工具和目录相同，预览后新增的文件也可能在确认阶段被意外移动。此外，多文件移动在
第二个或后续文件失败时会留下部分完成状态。

### 实现

- 新增 SQLite `pending_plans` 表，持久化规范化计划 JSON、SHA-256 计划哈希、状态和过期时间。
- 返回随机一次性令牌，数据库只保存令牌哈希，不保存令牌明文。
- 确认时通过 `BEGIN IMMEDIATE` 原子地将状态从 `pending` 转为 `executing`。
- 确认请求不再调用 LLM，而是重新校验并执行数据库中的原计划。
- 令牌默认十分钟过期；重复使用、过期、并发消费和计划完整性失败均拒绝。
- 文件预览保存具体 source/destination 清单，并纳入计划哈希。
- 执行前比较当前目录文件集合与预览快照；状态变化时要求重新预览。
- 新增 `file_transactions` 表，记录文件移动清单、完成步数和事务状态。
- 文件移动中途异常时按已完成步骤逆序补偿，并记录 `rolled_back` 或 `rollback_failed`。
- Gradio 改为“发送请求”和“确认执行预览计划”两个独立动作，令牌只保存在会话状态中。

### 验证结果

- `python -m pytest`：14 passed，耗时 1.34 秒。
- 覆盖一次性消费、重复令牌、持久化计划篡改、目录状态变化和模拟磁盘失败自动补偿。
- 36 个 Python 文件通过 AST 解析，FastAPI 与 Gradio 模块导入成功。
- 真实 Qwen3.5-4B 只读 CPU 查询成功，本次冷启动端到端耗时 18.38 秒。

### 技术取舍

- 令牌在执行前即被消费，避免网络重试造成重复副作用；代价是执行进程崩溃后不能直接重试。
- 计划绑定具体文件路径而不绑定文件内容哈希，因为当前操作只移动文件、不读取或改写内容。
- 当前自动补偿针对进程仍存活的异常；操作系统崩溃或断电需要启动时恢复器处理。

### 当前限制与下一步

- `executing` 状态的崩溃恢复尚未实现，需要根据事务清单判断继续、补偿或人工介入。
- 已完成事务尚未提供用户主动撤销接口。
- SQLite 数据库假设本地运行目录可信，尚未对计划记录增加独立 MAC 签名。
- Gradio 每个会话目前只保留一个待确认计划。
- 下一步实现事务恢复/主动撤销，再建立批量 Agent Eval 数据集。

## 2026-07-23：v0.3 可诊断、可撤销、可追踪、可评测

### 问题

v0.2 的工程安全性已经明显提高，但用户能看到的功能仍偏单点：查询一次 CPU、
移动一次文件。项目也缺少可以让招聘者复现的批量评测证据，已完成的文件事务
只能依赖人工恢复，API 请求出现问题时也难以定位具体执行记录。

### 实现

- 新增系统资源摘要、内存占用最高进程查询，并为“电脑卡顿”建立三步诊断计划：
  系统摘要、Top 进程、本地知识检索。
- 多工具完成后，把结构化 observation 交给本地模型生成“状态、可能问题、建议”报告；
  汇总提示明确禁止编造未观测数据。单工具调用不增加第二次推理开销。
- 新增已完成文件事务的撤销预览和高风险确认流程。撤销清单必须与原事务严格一致，
  文件缺失或原位置冲突时拒绝执行；撤销中途失败时尝试恢复撤销前状态。
- 新增 `agent_traces` 持久化记录和 `/traces` API，记录请求状态、计划哈希、端到端延迟、
  是否为确认请求以及 `trace_id`。追踪写入失败不会改变真实操作结果。
- 新增固定 80 条工具路由数据集与批量 runner，覆盖单工具、多工具、RAG、高风险操作、
  主动撤销和危险请求拒绝；输出工具准确率、参数准确率、安全拦截率、解析失败率、
  p50/p95 延迟，并保存模型配置与运行机器元数据。
- 本地模型路径、上下文、线程数和 GPU 卸载层数改为环境变量配置，上下文默认从 1024
  提升到 4096，以承载多工具提示与 observation 汇总。

### 验证命令与结果

- `.\.venv\Scripts\python.exe -m pytest -q`：18 passed，覆盖协议拒绝、一次性令牌、
  TOCTOU 防护、失败补偿、主动撤销、多 observation 汇总、trace 持久化和评测集结构。
- 真实 Qwen3.5-4B-Q4_K_M 路由冒烟：固定数据集前 2 条均正确，参数正确率 2/2，
  解析失败 0/2，平均 14.72 秒，p95 15.82 秒。样本过小，只证明 runner 链路可用。
- 完整 80 条严格 exact-match 基线：工具与参数准确率均为 93.75%，解析失败率 0%，
  危险请求拦截率 100%（7/7），p50 13.39 秒，p95 19.56 秒，总推理时间 1141.66 秒。
- 分类结果：单工具 36/36、高风险操作 16/16、危险请求 7/7、能力范围外 3/3；
  多工具诊断 9/10，RAG 4/8。详细失败审计见 `docs/evaluation/BASELINE_2026-07-23.md`。
- 真实“我的电脑最近很卡”端到端调用成功：模型选择三个工具并生成综合诊断，
  trace `5FtDSdyFVONPw9LT` 记录冷启动端到端耗时 90.28 秒。此次包含模型加载、
  embedding 加载、工具执行和第二次总结，说明功能可运行，也暴露了冷启动延迟问题。

### 技术取舍与失败证据

- 当前选择“模型规划、程序授权和执行、模型总结”的混合架构。安全边界不依赖小模型，
  但总结质量仍受 4B 模型影响。
- 已完成第一轮 80 条正式基线。5 条 exact-match 失败中，3 条属于“回答知识”与“立即诊断/
  执行”的意图边界不明确；不能为了提高分数简单修改标签或 prompt，需要先把数据集升级为
  显式 intent mode 或允许集合，再进行可比较的第二轮实验。
- `HuggingFaceEmbeddings` 当前出现 LangChain 弃用警告，功能不受影响，后续迁移到
  `langchain-huggingface` 并重建可复现依赖锁。
- trace 目前记录请求级结果，尚未把每一步 observation 单独建表；进程硬崩溃后的
  `running`/`undoing` 事务恢复也尚未完成。

### 下一步

1. 将评测标签升级为 `action/advice/diagnose` 意图模式和允许工具集合，再针对真实失败调优。
2. 增加 `trace_steps` 与 case replay，使线上失败能直接转成回归样例。
3. 实现启动恢复器，扫描悬挂事务并给出继续、补偿或人工介入状态。
4. 在已有单任务准入、软超时和取消基础上，评估任务状态持久化与 SSE 状态流。
5. 重建 RAG 索引与检索评测，增加稳定文档 ID、去重、阈值和来源命中率。

## 2026-09-08：v0.4 单机有界容量与协作式取消

### 问题

`/chat` 虽然已把同步 Agent 放入工作线程，但多个请求仍可能同时访问共享模型和桌面。
系统也没有活动任务 ID、状态查询或取消语义；直接对线程池 Future 设置超时会造成 API
认为任务结束、底层线程仍在运行的“假取消”。

### 实现

- 新增进程内 `AgentTaskManager`，原子接收一个活动任务，额外请求立即返回
  `503 agent_busy`，不创建等待队列。
- 新增 `POST /tasks`、`GET /tasks/{task_id}` 和取消接口；原 `/chat` 保持同步等待兼容，
  但必须通过同一个准入入口，不能绕过容量限制。
- 使用线程安全停止信号，在模型调用前后、工具步骤之间等安全边界检查取消和超时。
- 明确区分 `cancel_requested/timeout_requested` 与最终 `cancelled/timed_out`；工作线程真正
  返回前始终占用执行槽位。
- `/audit_log`、`/traces` 和精确 Trace 查询改在线程池中执行同步 SQLite 读取。
- Trace 增加 `queue_ms`、`model_ms`、`tool_ms` 和 `total_ms`，并为旧数据库执行兼容迁移。
- 内存任务记录保留最近 100 条；重启恢复和跨进程协调不属于当前版本。

### 验证

- `python -m pytest -q`：26 passed。
- 假任务阻塞期间，第二个 `/tasks` 和 `/chat` 请求均快速返回 busy，假 Agent 只执行一次。
- 推理线程阻塞期间 `/traces` 仍能返回。
- 请求取消或软超时后，只要假工作线程未真正退出，新任务仍被拒绝；线程退出后才释放容量。
- 测试使用假 Agent 和短时 sleep，不加载真实 llama.cpp 模型。

### 明确边界

- 取消与超时不是线程终止器，正在执行的同步模型或工具可能延迟响应停止请求。
- 任务状态位于单个 Python 进程内，不支持多 Uvicorn worker，也不在重启后恢复。
- 目前没有排队需求，因此 `queue_ms` 主要反映接受请求到工作线程启动的调度等待。
- 尚未测量真实模型 CPU 饱和时控制接口的尾延迟。

## 2026-09-15：RAG 检索边界与低置信度兜底

### 问题

原有 `query_knowledge_base()` 直接从 Chroma 取前三个文档并返回文本，缺少结构化的
匹配分数、命中问题和来源集合；当相似度不足时仍可能把弱匹配片段交给 Agent。

### 实现

- 将检索拆为候选归一化、匹配评分和答案决策三层。
- 新增 `retrieve_knowledge()` 与 `query_knowledge_base_detailed()`，返回候选答案、
  `confidence`、`matched_question`、`sources`、`retrieved_count` 和状态。
- 优先使用向量库相关性分数；不支持该接口时回退到普通相似度检索，并使用问答文本
  的可解释字符串相似度辅助排序。
- 低于阈值时返回 `low_confidence` 并主动拒答；原 Agent 工具仍保留纯文本接口，
  以避免破坏既有 Tool Calling 协议。
- 将 Chroma 与 embedding 导入改为懒加载，避免非 RAG 工具在启动时被模型依赖阻塞。

### 验证

- 新增 `tests/test_rag_query.py`，覆盖高置信度答案与来源、低置信度拒答、无相关性
  分数向量库回退。
- `python -m pytest -q`：29 passed。
- 新增 `evals/rag_dataset.jsonl` 与 `evals/run_rag_eval.py`，使用 15 条可回答问题和
  4 条负例扫描阈值。离线确定性检索器在阈值 0.35～0.45 时 Recall@2 为 93.3%、答案
  命中率 93.3%、precision 100%、负例拒答率 100%。
- 有 1 条“批量改名”的同义改写未命中，暴露字符相似度对语义改写的边界；暂不通过
  调低阈值掩盖问题，后续应使用真实 embedding 或同义词归一化验证。

### 边界

- 当前评分是轻量的候选排序与阈值机制，不等价于完整的 RAG 质量评测。
- 仍需继续扩充带标注的问题集，测量 recall/precision，并校准不同知识库规模下的阈值。
